# 일일보고서

> **버전 v2.2.1** — 변경 시 §버전 관리 규칙에 따라 bump 하고 **세 곳(본 파일 상단·`frame.html` 상단 주석·산출 아티팩트 footer)을 동기화**한다. 이력은 [CHANGELOG.md](CHANGELOG.md).
>
> **적용 범위: 프로젝트·패키지 무관 공용.** 어느 코드베이스 작업이든 같은 골격으로 보고하고, 도메인에 맞게 제목·범위·게이트·검증만 바꿔 채운다.

## 0. 설정 — 첫 실행 때 한 번만 묻는다

보고서를 만들기 **전에** [`~/.claude/chan-reports/report-config.json`](~/.claude/chan-reports/report-config.json) 을 Read 한다.

| 상태 | 할 일 |
|---|---|
| 파일이 있고 `author` 가 채워져 있다 | 그대로 쓴다. **묻지 않는다** |
| 파일이 없거나 `author` 가 비어 있다 | 아래를 **한 번에** 묻고, 답으로 파일을 만든 뒤 진행한다 |

> 보고서에 쓸 **이름**과 **직함**을 알려주세요 (예: `홍길동 / 주임`).
> PDF 를 공유드라이브에도 올리시려면 rclone remote 이름과 폴더 경로도요 — 안 쓰시면 "없음".

받은 답으로 이 형태를 그대로 쓴다(**한 번만**. 다음부터는 이 파일을 읽고 끝):

```json
{
  "author": "홍길동",
  "authorTitle": "주임",
  "org": "우리팀",
  "rclone": { "remote": "gdrive", "parent": "보고서/일일" },
  "uploadHtml": false
}
```

| 키 | 쓰이는 곳 | 비어 있으면 |
|---|---|---|
| `author` | 아티팩트 제목 · 헤더 작성자 · 파일명 · **드라이브 내 본인 폴더 이름** | **여기서 멈추고 묻는다** |
| `authorTitle` | 헤더 작성자 · 파일명 (아티팩트 제목엔 안 붙인다) | 직함 없이 이름만 |
| `org` | 푸터 `{{ORG}}` | 푸터에서 생략 |
| `rclone.remote` | rclone 에 등록한 드라이브 이름 | **업로드를 건너뛴다**(PDF 는 생성됨) |
| `rclone.parent` | **공유 부모 폴더.** 실제 업로드 경로는 `parent/author` | 〃 |
| `uploadHtml` | PDF 외에 HTML 도 올릴지 | `false` |

★**업로드 폴더는 `parent/author` 로 자동 조립되고, 없으면 `publish.ps1` 이 만든다**(`rclone mkdir`). 사람마다 **자기 이름 폴더**를 쓰므로 같은 부모 폴더를 공유해도 서로 덮어쓰지 않는다. 폴더 경로를 직접 적을 필요가 없다.

⚠️ **이미 있는 파일을 덮어쓰지 않는다** — 값을 바꾸고 싶다는 요청을 받았을 때만 고친다.

발행 스크립트(`publish.ps1`)가 없거나 rclone 미설정이면 **HTML 저장 + Artifact 발행까지만 하고 업로드는 건너뛴다** — 그 사실을 보고에 한 줄로 밝힌다.

## 0.1 드라이브 연결 — 사용자가 원할 때 내가 안내한다

사용자가 업로드를 쓰겠다고 했는데 `rclone.remote` 가 비어 있거나 연결이 안 되면, **아래를 순서대로 진행한다.** 문서 링크를 던지지 말고 **직접 확인하며 이끈다.**

| # | 누가 | 무엇을 |
|---|---|---|
| 1 | **내가** | `rclone version` 실행 → 버전이 나오면 3으로 |
| 2 | 사용자 | 없으면 `winget install Rclone.Rclone` → **터미널을 껐다 다시 연다**(PATH 인식). 그 뒤 내가 1을 재확인 |
| 3 | **내가** | `rclone listremotes` → 쓰려는 이름(예: `gdrive:`)이 이미 있으면 5로 |
| 4 | 사용자 | 없으면 **사용자가 직접** `rclone config` 실행 (아래 입력 순서를 그대로 제시한다) |
| 5 | **내가** | `rclone lsd <remote>:` → 목록이 나오면 연결 성공. **최상위 폴더 목록을 보여 주고 부모 폴더를 고르게 한다** |
| 6 | **내가** | `rclone lsd "<remote>:<parent>"` 로 그 부모 폴더가 실재하는지 확인 → `report-config.json` 에 `remote`·`parent` 기록 |
| 7 | **내가** | `rclone mkdir "<remote>:<parent>/<author>"` → `rclone lsd "<remote>:<parent>"` 로 본인 폴더가 생겼는지 확인 |

⚠️ **4번의 `rclone config` 는 내가 실행하지 않는다** — 대화형 TUI 라 응답을 못 주고 **멈춘다.** 사용자에게 아래를 그대로 제시하고, 끝났다고 하면 5번으로 검증한다.

```text
rclone config
  n                     (New remote)
  name  → gdrive        ← report-config.json 의 rclone.remote 와 같게
  Storage → drive       (Google Drive)
  client_id / client_secret → Enter (빈칸)
  scope → 1             (drive, 전체 접근)
  service_account_file → Enter
  Edit advanced config → n
  Use auto config → y   → 브라우저 열림 → 계정 로그인 · 허용
  Configure this as a Shared Drive (Team Drive)? → y → 대상 공유드라이브 선택
  확인 → q
```

**안 될 때**: `rclone` 을 못 찾으면 2번의 터미널 재시작을 먼저 확인한다(winget 이 추가한 PATH 는 새 세션부터 보인다). `rclone lsd` 가 비어 있으면 8번 단계에서 **Shared Drive 를 y 로 골랐는지**를 되묻는다 — 개인 드라이브로 연결하면 팀 폴더가 안 보인다.

## 1. 언제 쓰나

- 사용자가 **"일일보고서"** 류를 직접 요청할 때.
- 사용자가 **"커밋해"**(또는 commit / 커밋 / 커밋하자) 라고 할 때 — **커밋 직후 그날(YYYY-MM-DD) 보고서를 자동 생성/갱신한다.** 별도 요청 없어도 진행한다.

> **실행 방식**: **커밋은 foreground 로 먼저 완료·확인.** 그 뒤 보고서 생성/갱신은 백그라운드로 돌리고(HTML 작성 + Artifact 발행 위임) 완료되면 URL 만 전달한다. 사용자를 보고서 빌드로 블로킹하지 않는다.

### 커밋 트리거 세칙

- 그날 보고서가 **없으면 생성**, **있으면 그 커밋 작업을 카드로 추가**(넘버링·집계 칩·TOC/점프바 1:1 갱신).
- **브랜치명 재스캔 (필수)**: 생성/갱신 때마다 헤더의 "브랜치" 메타를 **현재 브랜치(`git branch --show-current`)로 다시 스캔해 갱신**한다. 초안이 임시 브랜치로 작성되는 경우가 기본이므로, 이후 브랜치가 rename 되면 갱신 시 현재 브랜치명으로 교체한다.
- 같은 날 보고서는 **동일 file_path 재사용** → 같은 아티팩트 URL 갱신.
- 커밋 내용 = 그 작업의 현상/원인/개선 결과로 카드화(§작업 단위 구성). 한 커밋에 여러 작업이면 대상 단위로 카드 분해(§작업 그룹핑).
- **검증 상태**: **커밋 지시는 사용자 수동 검증이 끝났다는 뜻이다.** 그 커밋에 담긴 작업 카드에는 `✓ 사용자 확인` 배지(`.verified`)를 유지하고, 검증 패널의 "사용자 수동 검증" 항목은 **완료(✓)** 로 적는다. "미검증 / 대기 / 미완" 으로 쓰지 않는다 — 사용자가 "검증 안 했는데 일단 커밋" 처럼 명시할 때만 미검증으로 남긴다.
- 사소(오타·포맷만)하거나 보고 가치 없는 커밋은 생략 판단 가능. 기능/버그/리팩토링/문서 커밋은 반영.
- 여러 커밋을 한 번에 지시하면 묶어서 그날 보고서에 반영.
- **발행 후 URL 기록 (필수)**: 발행/갱신한 뒤 **날짜 · 아티팩트 URL** 을 [`~/.claude/chan-reports/artifact-urls.md`](~/.claude/chan-reports/artifact-urls.md) 에 추가한다. weekly-report 스킬이 타임라인의 `↗ 일일 보고서` 링크를 여기서 조회한다. ⚠️ **Read 후 행만 추가한다** — 통째로 덮어쓰면 과거 행을 잃는다(실제로 한 번 잃었다).

## 2. 제목·파일명

### 아티팩트 게시글 제목 (필수)

HTML `<title>` 을 **`일일보고서 - {YYYY-MM-DD} {AUTHOR}`** 로 둔다. 예: `일일보고서 - 2026-08-24 홍길동`. 갤러리·브라우저 탭에 그대로 뜨며 날짜순으로 나열되고 누구 것인지 바로 보인다.

- **주제를 제목에 넣지 않는다** — 그날 주제를 딴 이름을 쓰면 갤러리에서 **일일보고서인지 알 수 없고** 날짜로 찾을 수도 없다. 주제는 헤더 `<h1>` 과 발행 `description` 의 몫이다.
- `{AUTHOR}` 는 직함 없이 이름만.

### 파일명 (필수)

`{YYMMDD}-일일보고서-{AUTHOR} {AUTHOR_TITLE}` — 날짜(2자리 연·월·일)가 **앞**, 그다음 문서 이름, 그다음 작성자. 예: `260703-일일보고서-홍길동 주임.html` / `.pdf`. 파일 목록이 날짜순 정렬되도록 날짜를 접두한다.

### 작업 제목 규칙 (필수)

`[TAG][현상]` 형식. **현상은 깔끔한 한 문장 평서문으로 쓴다.** 사용자 관점에서 **무엇이 어떠했는지 하나만** 말하고 끝낸다. 원인·경위·우회는 제목이 아니라 본문 **원인** 칸의 몫이다.

| 금지 | 왜 |
|---|---|
| `~해서 ~했던 문제` 같은 **이중절** | 원인과 현상을 제목에 함께 넣으면 길어지고 본문 원인 칸과 중복된다 |
| `~던 문제` · `~하는 문제` **접미** | 카드가 이미 문제를 다루므로 "문제"는 정보를 더하지 않는다. TAG 가 그 역할을 한다 |
| 쉼표로 이어붙인 두 사실 | 사실이 둘이면 카드가 둘일 신호다(§작업 그룹핑) |

- 종결은 **`~다`** (평서문). 명사형 나열(`… 맞바꾸기`)로 끝내지 않는다 — 무슨 일이 있었는지가 사라진다.
- 길이는 **한 줄** 안에. 제목이 두 줄로 넘치면 문장이 아직 두 개다.
- 본문엔 제목을 반복하지 않는다.

| ❌ | ✅ |
|---|---|
| `[BUG][목록을 새로고침하면 선택이 풀리던 문제]` | `[BUG][목록을 새로고침하면 선택이 풀렸다]` |
| `[FIX][저장 후 편집기가 깜빡이던 문제]` | `[FIX][저장하면 편집기가 깜빡였다]` |
| `[FEAT][삭제 시 확인 없이 지워지던 동작에 확인 모달 추가]` | `[FEAT][삭제할 때 확인 없이 바로 지워졌다]` |

> **FEAT 도 현상으로 쓴다** — "무엇을 추가했다"가 아니라 "그게 없어서 어떠했다". 개선 결과 칸이 무엇을 만들었는지 말하므로, 제목까지 산출물을 말하면 카드 안에서 같은 말이 두 번 나온다.

**목차·점프바의 짧은 제목도 같은 종결을 쓴다.** 레일은 한 줄로 잘리므로 **길이만 줄이고 문장 형태는 유지**한다 — 명사형으로 바꾸면 무슨 일이 있었는지가 사라진다. 목표 길이 **12~16자**(레일 폭 204px 에서 말줄임 없이 들어온다).

| 카드 제목 | ❌ 짧은 제목 | ✅ 짧은 제목 |
|---|---|---|
| `커넥트 종단끼리 자리를 맞바꿀 수 없었다` | `커넥트 종단 맞바꾸기` | `자리를 맞바꿀 수 없었다` |
| `문서 5건이 인덱스에 없었다` | `문서 신뢰도 정정` | `인덱스에 없었다` |

### TAG 의미 / 색

- `FEAT` — 새 기능 추가 (녹색)
- `BUG` — 잘못 동작하던 것 수정 (빨강)
- `FIX` — 동작/품질 보정·개선, 버그 단정 애매한 보정 포함 (파랑)
- `CHORE` — 빌드·의존성·도구·설정 (중립 회색)
- `DOCS` — 문서·룰·가이드 (슬레이트/청록)

> 문서/빌드/리팩토링 작업이 없으면 `CHORE`·`DOCS` 배지는 쓰지 않는다.

## 3. 넘버링 규칙 (강제)

- **모든 차례 번호는 두 자리 zero-pad** — `01 02 03 … 09 10`. 한 자리 금지.
- 작업 카드(01부터) → 영향 → 검증 순으로 **연속**. 영향·검증은 마지막 두 번호(작업 3건이면 영향 `04`·검증 `05`).
- **목차·점프바·본문 섹션 번호가 완전히 1:1** 이어야 한다. 제목은 `NN [TAG][현상]` 꼴.

## 4. 작업 단위 구성

- **현상**: 제목(`[TAG][현상]`)으로만 표현. **본문에는 현상 항목을 두지 않는다.**
- **원인**: 왜 그랬는지
- **개선 결과**: 어떻게 바뀌었는지 + 사용자 체감 결과

> **본문 표기 = 개조식(불릿) 강제.** 원인·개선 결과는 **줄글 금지** — 짧은 구·명사형/음슴체로 끊어 불릿 나열. 프레임의 `.val` 안에 `<ul><li>…</li></ul>` 로 렌더.

### ⚠️ 읽는 사람은 **의사결정자**다 — 개발 내부 얘기를 쓰지 않는다 (필수)

**판정 기준 한 줄** — *"이 문장이 읽는 사람의 판단을 바꾸는가?"* 아니면 쓰지 않는다.

| 쓰지 않는다 | 대신 |
|---|---|
| 파일명·함수명·게이트 이름 | 그것이 하는 일을 한국어로 |
| 내부 규칙 코드 (`R17`·`W5` 등) | 그 규칙이 막는 현상 |
| 커밋·PR 번호, 구현 방식(캐시·이벤트·디바운스) | 결과 수치와 사용자 체감 |
| "무엇을 어떻게 고쳤나" | **"무엇이 좋아졌나 / 무엇이 가능해졌나"** |

**한도 4개 (초과하면 줄인다)**

1. **카드당 불릿 4개** — 원인 2 · 개선 2.
2. **불릿 40자 이내 · 한 문장 한 개념** — `—` 부연, 괄호 근거 금지. 근거가 필요하면 그건 커밋 메시지·문서의 몫이다.
3. **강조(`<b>`)는 수치에만, 불릿당 1개** — 눈이 멈출 앵커를 하나만 둔다. **다 굵으면 안 굵은 것과 같다.**
4. **카드 수는 대상 단위로 3~4장** — 작업 건수가 아니라 *읽는 사람이 구분해 알아야 할 덩어리* 수다.

**수치는 문장에 넣지 말고 도식으로** — 성능·before/after 가 있는 카드는 `.figure`/`.ba` 로 뺀다. 문장에서 수치가 빠지면 저절로 짧아진다.

### ⚡ 개선 결과 패널 — 성능 수치는 **한 곳에 모아 맨 위에** (성능 개선이 있는 날 필수)

성능 수치를 카드 본문에 흩어 두면 눈이 카드마다 찾아다녀야 한다. `section.perf` 를 **핵심 정리 바로 아래**(작업 카드 위)에 두고 지표를 모은다.

- **지표 하나 = 카드 하나** (auto-fit 224px 그리드)
- 카드 구성 4단: **라벨**(무엇이) → **개선값**(크게, 주인공) → **감소율 배지** → **전후 미니바**
- **미니바 폭은 이전을 100% 로 본 비율**(개선÷이전×100). 짧아진 것이 그대로 보이므로 숫자를 안 읽어도 전달된다
- **3~6행.** 그보다 많으면 판단에 쓰는 것만 남긴다
- **항목 이름은 사용자 관점으로** — *"상대가 블록을 옮기면 내 화면에 뜨기까지"*(O) / *"store 델타 디바운스"*(X)
- **무번호(⚡)** — 작업 카드 번호(01~)는 그대로 아래에서 시작. 목차·점프바에도 무번호로 넣는다
- **성능 개선이 없는 날은 `section.perf` 를 통째로 삭제**한다(빈 패널을 남기지 않는다)
- 이 패널을 쓰면 **카드 본문에서 같은 수치를 반복하지 않는다**

## 5. 작업 그룹핑 규칙

- 작업 **4건 이하**: 그룹 헤더 없이 카드만 나열.
- 작업 **5건 이상**: 작업 도메인 기준 영역(예: "UI", "데이터/모델", "안정화")별 그룹 헤더로 묶는다.

### 카드 = 태스크(대상) 단위 — 보충·버그픽스 병합 (필수)

- **카드는 커밋이 아니라 "무엇을 만들었나"(태스크·대상) 단위**로 만든다. 같은 날 **같은 대상(기능/컴포넌트)** 에 대한 보충 구현·후속 버그픽스는 **별도 카드로 쪼개지 말고 그 대상의 큰 작업 카드 하나에 통합**해 설명한다.
- 보충/보정은 주 카드의 **개선 결과에 짧은 불릿으로 덧붙이는 정도**로. 사소한 후속을 별도 카드로 승격하지 않는다.
- **커밋 수와 무관**하게 대상 단위로 나눈다/합친다.
- **다른 대상**은 여전히 별도 카드 — 병합은 "같은 대상"에 한한다.

## 6. 핵심 정리 (맨 위 요약, 필수)

보고서 **맨 위**(헤더 집계 칩 바로 아래, 작업 카드 01 위)에 **핵심 정리** 패널을 둔다. 카드를 다 읽지 않아도 그날 한 일을 한눈에 보게 하는 목적.

- **종류(도메인)별 병합**: 그날 작업을 §작업 그룹핑과 같은 기준으로 **2~5개 그룹**으로 묶고, 그룹마다 **한 줄**로 요약한다. 개별 카드 내용을 반복하지 말고 **합쳐서** 쓴다.
- **형식**: 각 줄 = `분류` + 병합 요약 한 줄 + **관련 카드 번호**(두 자리, 클릭 시 `#wN` 으로 점프). 예: `복붙 — 연결 유실·중복·이름 초기화·붙여넣기 대상까지 정합화 [07][08][10]`.
- 작업이 적으면 분류 1~2개로도 충분. 억지 분류 금지.
- **TOC·점프바 최상단**에 `핵심 정리`(무번호, `★` 마커) 항목을 둔다 — 작업 번호(01~)는 그대로 카드부터 시작.

## 7. 줄바꿈(워드랩) 규칙 (필수)

- 한글은 **어절(공백) 단위로만 줄바꿈** — 글자 중간에서 잘리지 않게. 전역(`body`)에 `word-break: keep-all`.
- 긴 비분할 토큰(URL·경로·코드)만 넘칠 때 `overflow-wrap: break-word` 로 분할.
- 특히 **작업 카드 제목**: keep-all 로 단어 잘림 없이 줄바꿈(`text-wrap: balance` 병용). **글자 단위로 잘려 줄바꿈되는 것 금지.**
- 프레임에 이미 적용 — 그대로 쓰면 자동 반영.

## 8. 빈 항목 처리 규칙 (강제)

- **섹션 타이틀은 절대 삭제하지 않는다.** 내용이 없어도 섹션(영향·부작용, 검증, Breaking 등)은 그대로 두고 **내용에 '없음'류 문장을 필히 명시**한다 — 누락과 "해당 없음"을 구분한다.
- 강제 플레이스홀더(그대로 사용):
  - **부작용 없을 때** — 종합란: `알려진 부작용 없음`
  - **Breaking 없을 때**: `없음`
  - **미검증/후속 없을 때**: `없음`

## ★ 핵심 정리

- {분류 B} — {…} [NN]

---

## 01 [TAG][현상 제목]
**원인** — …
**개선 결과** — …

## 02 [TAG][현상 제목]

## 10. 스타일 가이드 (합의 누적)

- **헤더 메타**: `날짜 · 브랜치 · 범위 · 작성자` 순. 그 아래 **집계 칩** — **맨 왼쪽에 전체 작업 수**(액센트 강조 칩) + 이어서 TAG별 개수(0은 생략).
- **핵심 정리 패널**(집계 칩 바로 아래, accent-soft 박스): §핵심 정리.
- **현상은 카드 제목에만**. 본문은 **원인 → 개선 결과**를 위·아래 세로 배치하고, 각 칸은 **개조식 불릿(`<ul>`)** 으로.
- **원인·개선 결과 둘 다 카드(패널) 디자인** (원인=중립 톤, 개선 결과=액센트 톤).
- **왼쪽 플로팅 목차(TOC)** 필수: 작업 제목+영향+검증 나열, 클릭 시 스크롤 이동. 스크롤 위치에 따라 현재 항목 하이라이트(IntersectionObserver). `scroll-behavior:smooth` + `prefers-reduced-motion` 가드, 타깃에 `scroll-margin-top`.
- **TOC 반응형 3단 (강제)**: ①≥1260px 좌측 플로팅 레일 ②1024~1259px **레일 좌측 고정 + 본문 우측 시프트**(겹침 없이 플로팅 유지) ③<1024px 레일 숨김 → 상단 점프바 폴백. 아티팩트 뷰어 패널은 1260px 미만인 경우가 흔해 ②가 없으면 목차가 상단 알약으로만 보인다(회귀 사례 있음). **프레임의 미디어쿼리 3개(1260px·1023px·topnav 1023px)를 삭제·병합·임계 변경하지 말 것.** 발행 후 목차가 본문 왼쪽에 플로팅으로 보이는지 확인한다.
- **차례 넘버링** 필수(§넘버링 규칙).
- **영향 범위·부작용 점검 패널**을 검증 바로 위에: 수정 영역 체크목록(☑/☐) + 부작용 점검(✓/△) + 종합 판정 한 줄.
- 본문 **폰트 충분히 크게**, 문장 깔끔하게.
- 작업 카드별 TAG 배지 색 구분. (TAG 범례는 두지 않는다.)
- 코드 심볼·파일 경로 도배 금지. (영향 범위 패널의 파일 나열은 예외)
- self-contained(인라인 CSS, 외부 리소스 금지) — 아티팩트 CSP 준수.

### 색 토큰 (고정 — 보고서 간 동일 룩)

`:root` 에 아래 토큰을 박아 모든 보고서가 같은 팔레트를 쓴다(라이트). 다크는 `@media (prefers-color-scheme: dark)` **+ 뷰어 토글 대응 `:root[data-theme="dark"]`·`:root[data-theme="light"]`** 로 재정의한다(토글이 media query 를 양방향으로 이겨야 함).

정교한 **슬레이트 중성색 + 딥 틸(petrol) accent** — 중성색에 미세 청록 색조를 넣어 '선택된 회색'으로, accent(teal)·semantic·TAG 색은 분리:

```
ground #eef2f6 · panel #fff · panel-raise #f7fafc · ink #16222c · ink-soft #47586a · ink-faint #7a8a98 · line #d7e0e8
accent #0f6d78 (deep teal) · accent-soft #e1eff0 · accent-border #bcdadd
BUG #c0463b/#fbecea · FIX #2f6ab3/#eaf1fb · FEAT #2c7a51/#e8f4ed · CHORE #5c6976/#eef1f4 · DOCS #3a7a86/#e6f2f3
warn #b0701f · good #2c7a51
figure(before/after): before-ink #b1584c · after-ink=accent · diag-node #fff/#b7c4d0 · diag-edge #8496a6
그림자 3단계: --shadow-sm / --shadow-md / --shadow-lg
개선 결과 전용: --perf-* (이전=적색 / 개선=청록 두 축. 초록 배지 금지 — 개선값 청록과 구분이 안 된다)
```

하드코딩 색 금지 — 카드/패널 배경·테두리·그림자·도식 색 모두 토큰 변수로(다크 대응). ⚠️ **테마 블록 4개(light · media-dark · data-light · data-dark) 모두 정의** — 하나라도 빠지면 그 테마에서 색이 어긋난다.

### before/after 도식 (figure)

**수정이 실제로 어떻게 바뀌었는지**를 보여줄 때, 카드 안 `.rows` 다음에 `.figure` 블록을 둔다(선택). 레이아웃/배치/렌더 변경처럼 before→after 가 시각적으로 뚜렷한 작업에 유용. 인라인 SVG 를 `.d-*` 토큰 클래스(`d-box`·`d-box-b`·`d-box-a`·`d-edge`·`d-edge-b`·`d-edge-a`·`d-port`)로 그려 라이트·다크 자동 대응(외부 리소스 0, CSP 준수).

```html
<div class="figure">
  <div class="figure-cap">동작 변화</div>
  <div class="ba">
    <div class="ba-cell"><span class="ba-tag before">이전</span><svg viewBox="0 0 200 120">…d-box-b…</svg><div class="ba-note">{문제 한 줄}</div></div>
    <div class="ba-arrow">→</div>
    <div class="ba-cell"><span class="ba-tag after">개선</span><svg viewBox="0 0 200 120">…d-box-a…</svg><div class="ba-note">{개선 한 줄}</div></div>
  </div>
</div>
```

### 필수 폴리시

- **다크 모드**: `prefers-color-scheme: dark` 토큰 세트 제공.
- **인쇄/PDF**: `@media print` 로 점프바 숨김, 카드 `page-break-inside:avoid`, 배경 단순화. **목차는 숨기지 않고 본문 상단 정적 블록으로 노출** — `href="#id"` 앵커가 print-to-pdf 에서 PDF 내부 링크로 변환돼 **Drive PDF 뷰어에서 목차 클릭 이동**이 작동한다(Drive 는 JS HTML 을 서빙하지 않으므로 PDF 가 '그대로 보이며 목차 작동'하는 유일한 형태).
- **카드↔검증 연결**: 사용자 검증된 카드에 `✓ 사용자 확인` 마이크로 배지 → 검증 섹션과 1:1 대응.
- **좁은 화면 내비**: TOC 숨김(<1024px) 시 **상단 슬림 점프 바**(번호 칩, sticky)로 대체.
- **작업↔보고 메타 구분**: 작업 카드 다음, 영향·검증 패널 앞에 `검토 · 검증` 구분선.
- **개선 결과 위계**: 개선 결과 카드 라벨에 `→` 표식 + 본문보다 약간 강한 위계.

## 11. 재사용 프레임

완성 프레임은 **[`frame.html`](frame.html)** (이 폴더). CSS·토큰·TOC·점프바·인쇄·다크·스크립트가 모두 들어 있어 **복사하고 내용만 채우면** 매번 동일한 보고서가 나온다. **CSS/스크립트는 손대지 않는다(프레임 = 고정).**

채울 곳(플레이스홀더 `{{…}}`):

- 헤더: `{{TITLE}} {{DATE}} {{BRANCH}} {{SCOPE}} {{AUTHOR}} {{AUTHOR_NAME}}`, 집계 칩(전체 + TAG별).
- 핵심 정리: `section.summary` 의 `.sg`(분류 1개당)를 2~5개 복제. TOC·점프바 최상단 `핵심 정리`(★) 항목.
- 개선 결과: `section.perf` 의 `.perf-card` 를 지표 수만큼 복제. **성능 개선이 없으면 section 통째 삭제.**
- 작업 카드: `article.work` 를 작업 수만큼 복제 — `id=w1,w2…`, `wnum`/TAG/제목/`원인`/`개선 결과`. 검증된 작업만 `.verified` 배지 유지. 원인·개선 결과 `.val` 안은 **`<ul><li>…</li></ul>`**.
- 목차·점프바: 작업 1건당 항목 1개(번호·TAG·짧은제목) + 영향(N4)·검증(N5). 번호는 본문과 1:1.
- 영향 패널: 수정 영역 체크목록(☑/☐), 부작용 점검(✓/△), 종합 판정.
- 검증 패널: 자동 게이트 수치, 사용자 수동 체크, 미검증/후속.
- 번호: 작업 01·02… 다음 영향·검증이 마지막 두 번호.

## 12. 프로젝트 적용 가이드

특정 프로젝트 전용이 아니다. 어느 코드베이스든 같은 골격으로 보고한다.

- `{{PROJECT}}`(eyebrow)·`{{TITLE}}`·`{{SCOPE}}`·"수정한 영역" 체크목록을 **작업한 곳**에 맞게 채운다.
- **검증 게이트**: 그 프로젝트의 테스트/타입체크/린트 명령과 **실제로 돌린** 수치를 쓴다. 안 돌린 것은 지어내지 않는다.
- **선행조건(수동 검증 시)**: 그 프로젝트의 빌드 방식에 따른다 — 소스 직접 로드면 재오픈, 번들이면 빌드 후 리로드, 배포본이면 재배포.
- 프로젝트에 별도 수동 검증 절차 문서가 있으면 그 절차를 연계해 명시한다.

## 13. 절차

1. `frame.html` 복사 → `{{…}}` 채우고 반복 블록(작업 카드/목차 항목/체크)을 작업 수만큼 복제.
2. (필요 시) `artifact-design` 스킬 로드 — 단, **프레임이 이미 디자인을 고정하므로 레이아웃 변경 없이 내용만** 채운다.
3. Artifact 도구로 발행. 같은 날 갱신은 동일 file_path 재사용. **채운 HTML 은 `~/.claude/chan-reports/reports/{YYMMDD}-일일보고서-{AUTHOR} {AUTHOR_TITLE}.html` 로 저장**한다.
4. 발행 URL 을 `~/.claude/chan-reports/artifact-urls.md` 에 **Read 후 행 추가**.
5. **공유드라이브 업로드** — `./publish.ps1 -Html "<저장한 html 경로>"` 실행(PDF 변환 + 업로드, 같은 날짜 기존 것은 먼저 삭제해 1건만 유지). 스크립트·rclone 이 없으면 **건너뛰고 그 사실을 보고에 한 줄**.

## 14. 버전 관리 (SemVer 변형)

이 스킬(=골격·규칙·프레임)을 고칠 때마다 버전을 올린다. 보고서 *내용*이 아니라 **스킬 자체**의 버전이다.

- **MINOR +1, PATCH=0** — 새 기능 추가 또는 대폭 수정(섹션/구조/디자인 큰 변경).
- **PATCH +1** — 단순 수정(문구·소규모 스타일·플레이스홀더·오타).
- **MAJOR +1** — 전면 재설계 등 호환 불가한 변경.
- 변경 시 **반드시**: ① 본 파일 상단 버전 + ② `frame.html` 상단 주석 버전 + ③ 산출 아티팩트 footer 버전을 **동일 갱신**하고 [CHANGELOG.md](CHANGELOG.md) 에 한 줄 추가.
